# ADR-KEM-013 — Publish the `Idempotency-Key` pattern the API already enforces

| Field | Value |
| --- | --- |
| Status | **ACCEPTED 2026-09-24** — accepted by the programme owner (proposed 2026-08-24) |
| Date | 2026-08-24 |
| Raised by | karyalay-mail-ops `T00.07b`, from a live run against a running karyalay-mail |
| Affects | `tools/derive/gen_openapi.py`; 39 header declarations across four OpenAPI documents; every generated client; karyalay-mail §34.1's error selection |
| Approvers | Programme owner — **accepted 2026-09-24** |

## Context

`operations-api-v1.yaml` declares the `Idempotency-Key` header on C.101 as:

```yaml
- name: Idempotency-Key
  in: header
  required: true
  schema:
    type: string
    maxLength: 128
```

**`maxLength` and no `pattern`.** karyalay-mail §34.1 accepts RFC 3986
*unreserved* characters only — `A-Za-z0-9._~-` — and the published contract
does not say so.

That alone would be a documentation gap. Two further facts make it a defect
that breaks every conforming client, permanently.

**1. A malformed key is reported as a missing one.** The running service
answers `400 IDEMPOTENCY_KEY_REQUIRED` to a caller that is plainly sending the
header. `T00.07b` confirmed this against a real instance, through the real
§29.2 and §34.1 middleware over real mutual TLS — not against a fixture. A
caller reading that response has been told the exact opposite of what is wrong,
and will retry with the same key forever.

**2. The specification's own worked example is refused.** Repo 4 Appendix AP.1
writes `"idempotency_key": "case:...:mailbox-lock:v1"`. Colons are reserved
characters. **A client that implements the specification as written fails every
restriction request, and the error message points it in the wrong direction.**
C.101 is where this bites hardest, because the header is `required: true`
there — there is no path to a successful restriction for such a client.

Neither repository's test suite covered it. The enforced shape was published by
the contract, by karyalay-mail's spec and by karyalay-mail-ops' spec — by none
of the three.

**Half of this is already fixed, in the wrong place.** `v0.5.0` published
`actions/action-envelope-v1.schema.json` with the correct pattern on the
envelope's `idempotency_key` field:

```json
"idempotency_key": {
  "type": "string",
  "pattern": "^[A-Za-z0-9._~-]{1,128}$",
  "maxLength": 128
}
```

So the constraint is published, in the body of the action envelope, and absent
from the header of the operations that require the header. **One contract now
states the rule in one place and contradicts itself in another**, which is
worse than not stating it at all: a client generated from `operations-api-v1.yaml`
sees `maxLength: 128` and believes it.

## Decision

*Accepted as written by the programme owner on 2026-09-24. Until then this
heading read "Decision (proposed)"; the text beneath it is unchanged.*

**Publish the pattern on the header, from the one place that emits it.**

### 1. The generator, not the YAML

`openapi/operations-api-v1.yaml` carries `GENERATED by tools/derive/gen_openapi.py.
Do not hand-edit.` The fix is two `schema` dicts in that generator — the
required branch and the honoured-when-supplied branch, currently identical:

```python
IDEMPOTENCY_KEY_SCHEMA = {
    "type": "string",
    "pattern": "^[A-Za-z0-9._~-]{1,128}$",
    "maxLength": 128,
}
```

used in both places, then `npm run derive`. Nothing else in the generator
changes. **`maxLength` is kept alongside the pattern deliberately** — a
generated client that reads only `maxLength` still gets the length bound, and
tooling that surfaces `maxLength` in documentation keeps doing so.

### 2. One constant, referenced twice, not two literals

The value must be identical to `actions/action-envelope-v1.schema.json`'s. A
new harness check asserts exactly that: **the pattern on every
`Idempotency-Key` header equals the pattern on the envelope's
`idempotency_key`.** This is the `tools/derive/version.py` lesson applied to a
second field — the contract version had eight sources of truth and shipped two
different values in one tag; a key format with two sources will do the same.

### 3. karyalay-mail must stop misdescribing the failure

Publishing the pattern stops a *conforming* client from failing. It does not
fix the response a *non-conforming* client gets, and that response is what cost
the day. `IDEMPOTENCY_KEY_REQUIRED` means the header is absent. A present but
malformed header is a request-validation failure, and the catalog already has
the code for it: **`VALIDATION_FAILED` (422, `NON_RETRYABLE`)**, with the
malformed field named in the structured detail Repo 1 §39 already requires.

**No new error code is proposed**, deliberately. Adding
`IDEMPOTENCY_KEY_MALFORMED` would be an eighty-first code in a catalog that
ADR-KEM-005 was written to stop growing by invention, and `VALIDATION_FAILED`
with a field pointer says everything the caller needs.

This half is **karyalay-mail's to implement** and this ADR only records it as
required. The contract change without it leaves a caller that ignores the
schema still being told the wrong thing.

### 4. Appendix AP.1's example is wrong and its owner should fix it

`case:...:mailbox-lock:v1` cannot be made valid by any change proposed here.
Colons are excluded on purpose — the envelope's `$comment` records the reason:
*"a key that looks like a path or a URN is not treated as one by the next tool
that reads it."* The example needs rewriting in karyalay-mail-ops' Appendix
AP.1, e.g. `case.4f2a.mailbox-lock.v1`. **This repository does not edit that
appendix.** It is recorded here so the fix is not declared complete while the
document that misled the implementer still says what it said.

## Consequences

**39 header declarations change**, across four documents: `public-control-api-v1.yaml`
24, `mailbox-api-v1.yaml` 10, `internal-provisioning-api-v1.yaml` 3,
`operations-api-v1.yaml` 2. Eight are `required: true`; 31 are honoured-when-supplied.

**Wire compatibility: unchanged. Client compatibility: tightened, and that is
the point.** No request that karyalay-mail accepts today becomes invalid, and no
request it rejects today becomes valid. What changes is *where* a bad key is
caught: a generated client now refuses it locally with an accurate message
instead of sending it and receiving an inaccurate one. A client that was
constructing colon-bearing keys was already failing 100% of C.101 requests, so
there is no working caller to break.

**Version class: a minor release, additive-restrictive.** Published artifacts
change; no wire shape does. It cannot ride a patch, because a consumer that
regenerates gets stricter validation and must be told.

**Four consumers re-pin, and one has real work.** `karyalay-webmail` regenerates
its client. `karyalay-mail-ops` binds this on C.101/C.102 through
`internal/repo1client` and should assert the class in its own key derivation
([ADR-OPS-023](../../../karyalay-mail-ops/docs/adr/ADR-OPS-023-idempotency-key-derivation.md)
is where that lives). `karyalay-mail` implements §3 above. `karyalay-mail-infra`
is unaffected on this field, though it is pinned to `v0.2.1` and behind for
other reasons.

**Delta AI-01 moves from PARTIAL toward RESOLVED but does not arrive.** The
register records three open defects against AI-01; this closes one. The other
two are [ADR-KEM-014](ADR-KEM-014-restriction-precondition-token.md) and the
unraised containment gap.

## What was rejected

**Relax the server to accept the published `maxLength`-only shape.** This is
the other way to make the two agree, and it is wrong. RFC 3986 unreserved is a
deliberate choice with a stated reason: a key that looks like a path or a URN
gets treated as one by the next tool that reads it — a log parser, a cache key,
a URL builder. Widening the class to match a document that was simply missing a
line would trade a real safety property for the convenience of not editing a
generator.

**Publish the pattern and say nothing about the error code.** The pattern alone
would let this be declared fixed while a caller that does not read the schema
still gets told its header is missing. The misdescription is the part that cost
the day; the missing pattern is only what let it happen.

**Hand-edit the four YAML files.** They are generated, and the header says so.
A hand edit survives until the next `npm run derive` and then vanishes, which is
the same class of defect as hand-editing a converged host.

**The count was 40, not 39.** Consequences counted 39 declarations. `v0.6.0`
added C.117 `reportMessageFeedback`, a POST in the mailbox document, after this
ADR was written; its honoured-when-supplied header is the fortieth. By
document: public-control 24, mailbox 11, internal-provisioning 3,
operations 2. Eight required, 32 honoured when supplied.

**Scope, as karyalay-mail-infra asked.** Its run notes and ADR-INF-039 asked
for this to reach `internal-provisioning-api-v1.yaml` as well as the
operations document. It does: the generator emits every document, so all
three internal-provisioning headers (C.97, C.99, C.100) carry the pattern.

**One place still describes the key loosely.** `observability/telemetry-contract-v1.yaml`
gives the `idempotency_key` correlation identifier the format *"Opaque
client-supplied string, max 128 characters"*. That is not wrong, only less
specific than §34.1, and it is a hand-authored transcription of Master §20.5
prose that this ADR does not name. Left as it is and recorded here.
