# T00.11 — Decide ADR-KEM-003 (mailbox storage HA ceiling)

## Goal

Move ADR-KEM-003 from PROPOSED to ACCEPTED or REJECTED. This is an
architecture-owner decision (Narmesh), not an implementation task.

## Context

The ADR treats DRBD active/standby on Dovecot CE as a stage, not a
destination: deployments must publish their fencing capability before
claiming HA (no fencing → single-node with published RPO/RTO), and named
exit triggers decide when to move to a successor architecture. It affects
every Repo 3 HA/promotion task and the honesty of availability claims made
to customers.

Practical input needed for the decision: the actual VPS/hardware situation —
whether the hosting environment can provide real fencing (STONITH). That
fact determines whether the first deployment ships as fenced HA or as
single-node with published RPO/RTO.

## Steps

- ☐ Establish the fencing capability of the intended first deployment
  environment (provider, out-of-band power control or API equivalent) —
  *deliberately open: the ADR's acceptance does not depend on it; the fact
  is now tracked by Repo 3 T07.04/T07.08*
- ☑ Read the ADR's exit triggers and successor options
- ☑ Record the decision in the ADR file (status + date + rationale)
- ☑ Update the decision register row and the affected Repo 3 task rows

**Outcome (2026-08-17): ACCEPTED** by the architecture owner. The honesty
rule is binding: fencing proof before any HA claim; otherwise single-node
with published RPO/RTO. Repo 3 T07.04/T07.08 retain only the fencing-proof
blocker.

## Acceptance criteria

- ADR status is no longer PROPOSED; register and Repo 3 task tree reflect
  the outcome, including the published availability posture

## Evidence

Updated ADR file and decision-register row.
