# T00.08 — Domain record contract (`dns/`)

## Goal

Publish the machine-readable definition of every DNS record the platform
requires or verifies for a customer domain — the shared vocabulary behind
Repo 1's DNS-readiness state machine and Repo 3's authoritative zone
generation.

## Context

Repo 1 §10 verifies domain ownership and tracks DNS readiness; §11 manages
DKIM lifecycle metadata. Repo 3 generates and serves the records (NSD) and
enforces transport security (DANE/MTA-STS, its §33). Webmail displays
readiness states. All four surfaces must agree on record names, formats and
verification semantics.

## Steps

- ☐ Enumerate the record set from Repo 1 §10–§11 (verification TXT, MX, SPF,
  DKIM, DMARC) and Repo 3's transport-security sections (TLSA/DANE, MTA-STS,
  TLS-RPT)
- ☐ Define `dns/records.schema.json`: record type, name pattern, value
  grammar, TTL guidance, verification rule, readiness-state mapping
- ☐ Reconcile Repo 1's readiness states against Repo 3's zone/generation
  behaviour; discrepancies become ADRs
- ☐ Note DMARCbis alignment (RFC 9989-series citations in the specs) without
  editing any spec

## Acceptance criteria

- Every record type any spec mentions for customer domains appears exactly
  once, with a verification rule
- Readiness-state mapping validated against Repo 1 §10's state machine

## Evidence

Harness validation output; reconciliation note.
